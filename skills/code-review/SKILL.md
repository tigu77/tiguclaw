# Code Review · 버그 진단 방법론

비서가 코드 버그를 진단하거나 리뷰할 때 따르는 절차. **간결함을 유지하되 correctness 는 절대 놓치지 않는다.**

## 1. 근본 원인 진단 (증상 아닌 원인)

- 증상("모드가 Normal 로 나감")이 아니라 **왜 그 값이 그렇게 되는지 메커니즘**을 짚는다. 관련 코드 흐름(생성·전달·소비 지점)을 추적해 *실제 원인*을 특정한다.
- "여기서 이렇게 채워지고 → 저기서 이렇게 재계산되어서 → 값이 섞인다" 처럼 **경로**로 설명한다. 추측 금지 — 코드를 읽고 확정한다.

## 2. ★확장 점검 (correctness — 항상 한다)

**같은 근본 원인이 인접한 필드·경로·호출부에도 있는지 반드시 확인한다.** 하나만 고치고 형제 버그를 남기지 마라.

- 예: `GameMode` 가 "종료 시점 재계산"이라 stale 이면 — **같은 방식으로 채워지는 `Round`·`Level` 도 stale 아닌가?** 를 반드시 본다. (실제로 이걸 놓쳐서 반쪽 수정이 된 사례가 있다.)
- 체크리스트: "이 값이 이렇게 잘못됐다면, *같은 패턴으로 만들어지는 다른 값들*도 같은 함정에 빠지지 않나?" — 명시적으로 훑는다.
- 이건 취향이 아니라 **정확성**이다. 확장 점검을 건너뛰면 잠재 버그를 남긴다.

## 3. 최소 수정 제시

- **코드베이스의 기존 관용구·패턴에 맞춰** 수정한다 (예: 이미 `xxxCache` 캐싱 패턴이 있으면 그걸 따른다). 새 추상화를 함부로 들이지 않는다.
- 건드리는 범위를 최소화하고, **정확히 어느 파일·어느 줄**을 어떻게 바꾸는지 명시한다.

## 4. 견고한 방향 (짧게 — 옵션)

최소 수정과 *별개로*, 재발을 줄이는 방향을 **1~3줄로 절제해서** 덧붙인다:

- **진실 소스 정합** — 이 데이터의 authoritative 한 출처가 어디여야 하나 (세션 시작 스냅샷? 서버?).
- **검증 위치** — 클라이언트만으로 충분한가, 서버가 최종 검증해야 하나.
- **재발 방지 구조** — 흩어진 상태를 한 컨텍스트 객체로 묶는 등.

⚠️ **분량 절제.** 최소 패치를 원하는 사용자에겐 장문의 구조 제안이 소음이다. 견고한 방향은 *짧게 제시*하고, 사용자가 원하면 더 파고든다. correctness(1·2)는 항상, 깊이(4)는 짧게 — 이 균형이 이 스킬의 핵심이다.

## 요약 원칙

> 근본 원인을 정확히 → **같은 원인이 인접 필드/경로에도 있는지 확장 점검**(필수) → 관용구에 맞는 최소 수정 → 견고한 방향은 짧게 옵션. 간결하되 형제 버그를 남기지 않는다.
