# 코드 리뷰

리뷰는 **읽는다. 고치지 않는다.** 결과물은 «확인된 발견» 목록이다 — 확인 동작을 돌린 것만.

## A. 범위 — 먼저 한 줄로 선언한다

- 대상: 사용자가 가리킨 것(경로·PR·브랜치·커밋 범위·파일 목록). 말이 없으면
  **아직 반영 안 된 변경분** — 버전 관리가 있으면 그 미커밋 변경(`git diff` + 미추적 파일
  등), 없으면 **무엇을 볼지 한 줄로 묻는다.** ★버전 관리를 전제하지 마라: 이 스킬은 레포가
  아닌 폴더에도 쓰인다.
- 기본 범위 = **diff + 바뀐 심볼의 직접 호출부 + 그 심볼을 이름으로 부르는 검사.**
  그 밖(변경 이력·인접 모듈·설계 문서)은 사용자가 «깊게·넓게·전부·이력까지» 라고 할 때 연다.
  요청보다 좁히지 말고, 요청 없이 넓히지 마라.

## B. 몇 명이 읽나

★**시간은 비용이 아니다. 비용은 같은 글을 두 번 읽는 것과 사람 수다.** 오래 걸려도 되니
겹치지 않게 하라.

- **기본은 0명** — 이 컨텍스트가 직접 읽는다. 혼자가 가장 정확하고 가장 싸다.
- 혼자 담기 어려울 만큼 크면 **파일 묶음**으로 나눈다. 묶음 = 디렉터리·모듈 단위의
  **서로 겹치지 않는 파일 집합**(호출부가 묶음 안에 머물도록 자른다). 한 묶음 = 한 명.

      사람 수 = min(겹치지 않는 파일 묶음 수, 3)

- ★**3은 천장이지 정원이 아니다.** 묶음이 하나면 한 명이다. **3을 채우려고 묶음을 쪼개지
  마라** — 억지로 나누면 파일이 겹치고, 겹치면 같은 것을 두 번 읽는다.
  **먼저 자연스럽게 묶고, 그 다음에 자른다.** 반대로 하면 매번 천장을 채우게 된다.

### ★나누지 않는 두 가지 — 지시가 없으면 이 둘이 기본값으로 나온다

1. **관점으로 나누기**(정확성·단순화·효율·검사 공백을 각각 한 명에게) — 넷이 **같은 diff**
   를 읽으므로 읽는 양이 사람 수만큼 곱해진다. 관점은 **한 명의 체크리스트**다(§C).
2. **발견 수에 비례해 띄우기**(발견마다 검증자 N명) — 발견은 열기 전엔 개수를 모르므로
   상한이 없다. 검증은 사람이 아니라 **동작**으로 한다(§D).

### 팬아웃 배관

2명 이상이면 리뷰 **전체**를 매니저에게 `run_in_background` 로 넘기고, 그 안에서 묶음마다
`spawn_agent` 한다(서브는 다시 못 띄운다 — depth 1).
**전부 띄운 뒤** `wait_for_worker([jobId, …])` 로 한 번에 합류한다 — `spawn_agent` 은 즉시
jobId 를 주고 기다리지 않으므로, 하나씩 띄우고 합류하면 줄을 선다.

★**프롬프트는 `references/review-orchestration.md` §1·§2 를 그대로 쓴다 — 즉석에서 짓지
 마라.** 이 파일(`invoke_skill` 이 주는 본문)엔 템플릿이 없다. 즉석 작성은 담당 파일·출력
 형식이 매번 달라지고, 그 차이는 조용하다.
★서브에겐 **규칙을 한 벌만** 준다 — 템플릿이 `invoke_skill` 을 시키므로 이 문서를 프롬프트에
 **복사하지 마라**(같은 글을 두 번 싣는 것은 이 스킬이 금지하는 바로 그것이다).

보고서에 **띄운 수와 묶음 목록**을 적는다. 묶음을 못 적으면 띄울 이유가 없던 것이다.

### 사용자가 넓히라면 넓힌다

★**위 규칙은 네 자기 판단을 묶는 것이지 사용자를 막는 문이 아니다.** 사용자가
«빨리·한 번에·넓게» 를 말하면 **넓혀라.** 값만 한 줄로 말하고 **그대로 진행**한다
(되묻고 멈추지 마라 — 아는 채로 고르게 하는 게 목적이다):

> "N명으로 넓힙니다 — 사람마다 스캐폴딩이 한 벌씩 더 실립니다."

넓혀도 **겹침 금지는 그대로**다. 사람을 늘리는 방법은 **파일을 더 잘게 나누는 것**이지
같은 파일을 여럿에게 주는 것이 아니다.

## C. 무엇을 보나 — 다섯 축

정확성·가독성·성능·중복은 안 적어도 본다. 아래는 **안 적으면 안 보는 것**들이다.
각 항목은 «어느 파일·어느 줄» 로 답할 수 있을 때만 발견이 된다.

★**경계는 «읽는 범위» 가 아니라 «보고하는 범위» 다.** 발견은 자기 파일에 대해서만 내되,
**읽기·grep 은 아래 축이 요구하는 만큼 나간다**(검사 파일 · 호출부 · 이웃). 읽기까지 묶으면
축 1 은 «검사 없음» 을 양산하고 축 5 는 침묵으로 닫힌다 — 고치려던 것보다 나쁘다.

1. **검사는 「있나」가 아니라 「도나」.** 바뀐 줄마다: 이 줄을 되돌리면 어느 검사가
   빨개지나 — **이름을 대라.** 못 대면 그 줄은 검사 밖이고, 그것 자체가 발견이다.
   항상 초록인 검사(단언 없음 · 설명문을 대상으로 세는 검사)는 없는 검사다.
2. **부품이 아니라 이음매.** 함수 본체보다 **부르는 쪽과의 계약**을 본다.
   시그니처·반환 형태·예외·기본값이 바뀌었으면 **호출부 전수**(grep 으로 세고 그 수를
   적어라). 조건이 뒤집히거나 가드가 생겼으면 **그 분기에 도달하는 입력 전수**.
3. **수정이 낳은 결함.** diff 가 «고치기» 라면, 고치려던 것이 고쳐졌나와 **별개로**
   그 수정에 의존하던 것이 안 깨졌나. 새로 든 값·상태는 그것을 읽는 모든 분기에 닿나.
   수정도 새 코드이므로 원래 결함보다 결함이 많기 쉽다.
4. **손으로 관리하는 목록.** 새로 생긴 이름 열거·허용 목록·분기 나열은 낡을 시계가
   시작된 것이다. 정의점에서 파생시킬 수 있으면(파일시스템·타입·설정) 그렇게 하라고 짚는다.
5. **같은 원인의 이웃.** 결함 하나를 찾았으면 **같은 패턴을 grep 으로 인접한 곳에서 한 번**
   찾는다. 확장은 거기서 멈춘다.

## D. 발견을 세우는 법 — 주장이 아니라 확인

발견은 **한 동작으로 확인 가능한 주장**이어야 한다.

```
[결함|그물|정리] path/file.ts:LINE
주장: 한 문장 — 무엇이, 어떤 입력에서, 어떻게 틀리나
확인: 한 동작 — grep 한 줄 / 파일 한 곳 읽기 / 검사 한 번
결과: 확인됨 | 기각        ← 확인 동작을 **실제로 돌린 뒤** 적는다
수정안: 한 줄, 코드베이스 관용구 안에서 최소. 여기서 고치지 않는다.
```

- **결함** = 사용자에게 닿는다. **그물** = 코드는 지금 맞지만 검사가 못 잡는다.
  **정리** = 중복·단순화·재사용(동작 안 바뀜).
- ★**확인 동작을 돌리지 않은 발견은 보고하지 않는다.** 이것이 적대적 검증이다 — 사람을
  더 띄우지 않고, diff 를 다시 읽지 않고, 발견마다 동작 하나를 실행한다.
  매니저 구성이면 **매니저가 서브의 «확인» 줄을 직접 돌려** 검증하고 합친다(중복은 하나로).
- 확인 동작을 만들 수 없는 주장(경합·타이밍 등)은 **«의심»** 으로 맨 끝에 한 줄씩.
  확신도 숫자는 적지 않는다 — 자기 채점은 감사할 수 없다. 확인됨/기각/의심 셋뿐이고,
  애매하면 주장을 더 쪼개라.

## E. 보고

보고 끝에 **두 줄**을 반드시 붙인다. 둘 다 «행동을 바꾸는» 줄이다:

```
띄움: N명 (묶음: …)          ← 묶음을 못 적으면 띄울 이유가 없던 것이다
안 고침: 확인함 (리뷰 전후 대조 — 무엇으로 쟀는지 함께)
```

★**집계 숫자(제기 N·기각 N)는 안 적는다.** 확인/기각은 **발견마다** 붙는 것으로 족하고,
합계는 해석이 안 된다 — 기각 0이 «발견이 좋았다» 인지 «반증을 안 했다» 인지 못 가르고,
어느 쪽이든 할 일이 달라지지 않는다. 행동을 안 바꾸는 관측은 적지 않는다.

아래에 확인된 발견을 **결함 → 그물 → 정리** 순으로. 기각된 것은 수만 적는다(사용자가
물으면 목록을 준다).

★**발견 0건이면 §C 다섯 축을 «축이 요구하는 값» 으로 닫는다** — 안 봤는데 0건인 것과
보고도 0건인 것은 다르다. «봤다» 는 산문은 검증할 수 없으니, 축이 원래 시키는 **결과물**을
적는다:

    1 검사가 도나   → 바뀐 줄을 덮는 **검사 이름**(못 대면 그게 발견이다)
    2 이음매       → 계약이 바뀐 심볼과 **호출부 수**(안 바뀌었으면 «계약 변경 없음»)
    3 수정이 낳은  → 이 diff 가 고치기인가 아닌가, 맞으면 무엇에 의존하던 것을 봤나
    4 손 목록      → 새로 생긴 열거·허용 목록의 **개수**(0이면 0)
    5 이웃         → 돌린 **grep 패턴**(발견이 없었으면 «해당 없음»)

## F. 하지 않는 것

- **파일을 쓰지 않는다** — 작업 트리·stash·브랜치·임시 파일 전부.
  `Bash` 는 **읽는 명령만.** 판정은 이름 목록이 아니라 **«이 명령이 무엇을 바꾸나»** 다 —
  아무것도 안 바꾸면 써도 된다(예: `grep`·`sed -n`·`nl`·`cat`·`ls`, 버전 관리가 있으면
  `git diff/show/log/blame`) ·
  기존 검사 실행. **금지**: `>` · `>>` · `tee` · `sed -i` · `perl -i` ·
  `git checkout/stash/reset/apply/commit` · 빌드 산출물을 쓰는 명령.
  검사를 «변이로 뚫어보는» 것도 **머리로** 한다(§C-1 은 이름을 대는 것이지 고치는 게 아니다).
  ★**«안 고쳤다» 를 말로 하지 말고 대조해서 보여라** — 리뷰 **전**에 상태를 한 번 뜨고,
  **끝에** 다시 떠서 같음을 §E 에 적는다. **재는 수단은 대상이 정한다**:
  버전 관리가 있으면 그것(`git status --porcelain` 등), 없으면 대상 파일의
  크기·수정시각 목록이면 된다. **도구를 못 박지 않는 이유**는 리뷰 대상이 늘 레포인 것도
  아니고 늘 git 인 것도 아니어서다 — 못 재는 대상이면 그렇게 적어라(«대조 불가: 이유»).
  ★«못 재니까 생략» 은 안 된다. 생략하면 그 줄이 있던 이유가 사라진다.
- **같은 파일을 두 사람에게 읽히지 않는다.**

## G. 액션 (사용자가 명시했을 때만)

★리뷰 자체는 아무것도 안 고친다. 아래는 사용자가 **명시**한 경우에만, **메인이** 한다 —
서브는 이 플래그를 받지도, 스스로 판단해 고치지도 않는다.

| 플래그 | 배선 | 규칙 |
|---|---|---|
| `--fix` | `Edit`/`Write` 로 작업 트리 적용 | **확인됨만**, 파괴적이므로 적용 전 사용자 승인. 발견별 적용/스킵 선택 |
| `--comment` | github MCP 인라인 PR 코멘트(있으면) | 없으면 마크다운 폴백(§H) |
| `--commit` | `--fix` 적용 후 커밋(버전 관리가 있을 때만) | 메시지에 리뷰 근거 요약. 사용자 승인 후 |

그 수정은 **새 diff 이므로 다시 이 스킬의 대상**이다.

## H. 외부가 실패해도 리뷰는 산다

- **서브 사망** → 나머지 묶음은 그대로 진행, 보고에 «미검토 파일: X» 한 줄.
  어느 파일을 못 봤는지 **이름으로** 남겨라 — «리뷰했다» 가 «그 파일은 아무도 안 읽었다» 를
  덮으면 안 된다.
- **MCP·외부 도구 부재** → 마크다운으로 내용을 그대로 반환한다(리뷰를 버리지 않는다).
- **확인 동작이 실패**(검사가 안 돌거나 grep 이 막힘) → 그 발견은 «의심» 으로 내린다.
  검증 실패가 발견을 **지우면** 안 된다 — 그러면 도구가 부실할수록 보고가 깨끗해 보인다.
