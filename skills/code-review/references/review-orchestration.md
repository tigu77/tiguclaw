# review-orchestration — 팬아웃 프롬프트 본

`SKILL.md` §B 에서 참조. **2명 이상일 때만** 쓴다 — 기본은 0명(직접 읽기)이다.

---

## 1. 매니저에게 넘기기

서브가 2명 이상이면 리뷰 **전체**를 넘긴다(팬아웃은 매니저 안에서 — 서브는 다시 못 띄운다).

```
run_in_background({
  label: "<범위> 코드 리뷰",
  prompt: `
[모드: 코드 리뷰 오케스트레이션]
대상: {GIT_RANGE}

1) `git diff --stat {GIT_RANGE}` 로 변경 파일을 뽑아, **겹치지 않는 파일 묶음**으로 나눠라
   (디렉터리·모듈 단위. 호출부가 묶음 안에 머물도록 자른다).
   사람 수 = min(묶음 수, 3). ★묶음이 하나면 한 명이다 — 3을 채우려고 쪼개지 마라.
2) 묶음마다 아래 §2 프롬프트로 spawn_agent 한다 — **전부 띄운 뒤**
   `wait_for_worker([jobId, …])` 로 **한 번에** 합류한다(`spawn_agent` 은 즉시 jobId 를
   돌려주고 기다리지 않는다. 하나씩 띄우고 합류하면 줄을 선다).
3) 서브가 낸 발견의 «확인» 줄을 **네가 직접 돌려** 검증하고, 중복은 하나로 합쳐라.
4) 확인된 발견을 **결함 → 그물 → 정리** 순으로 보고하고, **끝에 이 두 줄을 붙여라**:

       띄움: N명 (묶음: …)
       안 고침: 확인함 (spawn 전 == join 후 — 무엇으로 쟀는지 함께)

   ★대조는 **네가** spawn **전과** join **후에** 한 번씩 떠서 한다(수단은 대상이 정한다 —
    버전 관리가 있으면 그것, 없으면 파일 크기·수정시각 목록) —
    서브에게 «네가 안 고쳤음을 증언하라» 고 시키면 제약받는 당사자의 자기 증언이 된다.

★너와 서브 전부 **읽기 전용**이다.`
})
```

## 2. 묶음 서브 프롬프트

```
spawn_agent({
  name: "code-review",
  prompt: `
[모드: 파일 묶음 리뷰 — {GROUP_NAME}]
대상 범위: {GIT_RANGE}
★**네 파일**(이것만 본다 — 나머지는 다른 서브 몫이다):
{FILE_LIST}

먼저 invoke_skill 로 code-review 스킬을 로드해 §C·§D·§F 를 지켜라.

★스킬 §C 다섯 축을 **네 파일에 대해 전부** 본다(축은 사람을 나누는 기준이 아니라
  네 체크리스트다). 축의 정의는 스킬에 있다 — 여기 다시 적지 않는다(두 벌이 되면 갈린다).
★**발견마다 「확인 동작」을 실제로 돌린 뒤에만** 보고한다(§D). 안 돌린 주장은 내지 마라.
★★**너는 아무것도 고치지 않는다.** Bash 는 읽는 명령만(`git diff/show/log/blame`·`grep`·
  `sed -n`·`nl`·`cat`·기존 검사 실행). `>`·`tee`·`sed -i`·`git checkout/reset/apply` 금지.
★**서브에이전트를 띄우지 마라.**
★네 파일 밖으로 나가지 마라 — 예외는 §C-2 의 호출부 grep 뿐이다(그건 네 파일의 계약을 좇는 것).

발견을 아래 JSON 배열로만 반환(없으면 [] — 그리고 다섯 축을 각각 어떻게 닫았는지 한 줄씩):
[{ "kind": "결함|그물|정리", "file": "...", "line": 42, "axis": 1-5,
   "claim": "무엇이, 어떤 입력에서, 어떻게 틀리나",
   "check": "실제로 돌린 한 동작(못 만들면 «만들 수 없음: 이유»)",
   "result": "확인됨|기각|의심",
   "fix": "관용구 정합 최소 수정(어느 줄 어떻게)" }]`
})
```

## 3. 집계 (매니저가)

- 서브의 `result: "기각"` 은 보고에서 빼고 **수만** 센다.
- `확인됨` 이라도 **매니저가 그 «확인» 동작을 한 번 더** 돌린다 — 돌려서 안 맞으면 기각으로
  내린다. 이것이 이 구성의 적대적 검증이고, 사람을 더 띄우지 않는다.
- 확인 동작을 만들 수 없었던 것은 «의심» 으로 맨 끝에.
- 서브가 죽으면 그 묶음은 «미검토 파일» 로 이름을 남긴다(§H).

## 4. 왜 이 모양인가 (한 줄씩)

- **관점으로 나누면** 여럿이 같은 diff 를 읽어 읽는 양이 사람 수만큼 곱해진다.
- **발견 수로 나누면** 상한이 없다 — 발견은 열기 전엔 개수를 모른다.
- **파일로 나누면** 겹치지 않으므로 사람이 늘어도 읽는 총량이 안 는다(고정비만 는다).
- **검증을 동작으로 하면** 사람이 안 늘고, 확인/기각이 **발견마다** 남는다.
