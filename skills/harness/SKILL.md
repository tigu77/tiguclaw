# Harness — 재사용 팀 제작 가이드

## 1. 적용·영속화 경계 — 구축 전에

**일반 위임 판단의 정본은 SYSTEM.md §1**이다. 직접/1명/팀 판정과 매니저 배치를 여기서 다시 정의하지 않는다. 위임·합류·추가 지시·알림의 계약은 현재 제공되는 도구 설명을 따른다.

- **이번 한 번의 역할은 프롬프트로 전달한다.** 일회성 작업 때문에 에이전트 파일이나 팀 스킬을 만들지 않는다.
- **반복해서 사용할 팀만 영속 자산으로 만든다.** 재사용 의도가 불분명하면 파일을 쓰기 전에 확인한다. 팀 규모 자체가 영속화의 근거는 아니다.
- 기존 팀을 실행하려는 요청이면 그 오케스트레이션 스킬을 사용한다. 이 제작 가이드를 매번 로드하지 않는다.
- 삭제·이동·외부 영향 등은 SYSTEM.md의 승인 규칙을 따른다. 템플릿이 승인을 대신하지 않는다.

## 2. 기존 역할과 저장 위치 확인

가용 에이전트·스킬 인덱스를 먼저 보고, 프로젝트 전용이면 `project_capabilities(path)`로 해당 폴더의 자산을 확인한다. 역할이 같으면 재사용하고, 범위만 넓힐 때는 기존 호출부에 미칠 영향을 확인한다. 실제로 다른 역할만 새로 만든다.

자산 경로는 SYSTEM.md §5를 따른다. 사용자가 프로젝트 전용을 지정하지 않으면 홈 공통이 기본이다.

| 자산 | 홈 공통 | 프로젝트 전용 |
|---|---|---|
| 에이전트 정의 | `<TIGUCLAW_HOME>/agents/<name>.md` | `<project>/.tiguclaw/agents/<name>.md` |
| 오케스트레이션 스킬 | `<TIGUCLAW_HOME>/skills/<name>/SKILL.md` | `<project>/.tiguclaw/skills/<name>/SKILL.md` |

프로젝트는 폴더에 들어가야만 발견되는 것이 아니다. 다른 폴더의 자산도 `invoke_skill(name, path)`·`spawn_agent(name, prompt, path)`로 발견한 경로를 지정해 사용한다. 정확한 인자 형식은 각 도구 설명을 따른다.

## 3. 역할·입출력·산출물 연결 구성

재사용 팀은 기존/신규 에이전트 정의와 하나의 오케스트레이션 스킬로 구성한다. 별도 team 파일은 만들지 않는다.

1. 전문성·컨텍스트·재사용성을 기준으로 역할을 구분한다. 읽거나 쓰는 파일이 겹치면 합칠 수 있는지 먼저 본다.
2. 각 역할의 책임, 최소 도구, 입력, 출력, 실패 보고를 정한다. 프로파일은 작동 컨텍스트의 **실제 가용 이름**을 선택한다. `provider:model` 직접 지정은 특정 모델 고정이 필요한 경우에만 사용한다. 미지정은 기본 모델이며 `high/mid/low`만 유효하다고 가정하지 않는다.
3. 오케스트레이션에 호출할 이름·프로젝트 `path`·선후 의존성·산출물의 필수/선택 여부를 적는다. 앞 단계 출력과 다음 단계 입력의 절대 경로를 연결한다. 짧은 결과는 합류 반환값으로 수집할 수 있다.
4. 필수 산출물이 없거나 검증에 실패하면 그 결과에 의존하는 단계와 완료 보고를 차단한다. 선택 산출물만 누락과 영향 범위를 밝히고 진행할 수 있다.
5. QA 역할은 필요한 경우에만 기존 역할을 재사용하거나 구성한다. 모든 팀에 자동 추가하지 않는다.

개별 스킬의 형식·description·트리거 설계는 **`skill-creator`**가 정본이다. **변경 이력은 `git log`**로 남기며 본문에 이력 표를 중복하지 않는다.

필요한 참고만 읽는다:
- 역할·패턴·정의 예시: `references/agent-design-patterns.md`
- 워크플로우·입출력·실패 처리 예시: `references/orchestrator-template.md`
- QA 역할을 선택한 경우의 참고: `references/qa-agent-guide.md`

## 4. 연결 검증과 보고

실행 검증 절차는 **`verify`**를 따른다. 제작한 자산에 대해서는 다음 연결을 확인한다.

- 파일 경로·frontmatter·호출 이름·프로젝트 `path`가 실제 발견/로드 결과와 일치하는가
- `model`이 실제 가용 프로파일 또는 의도한 `provider:model`인가(미지정/`default`는 기본 모델), 도구가 역할에 필요한 최소인가
- 입력·출력 경로와 필수/선택 의존성이 끊기지 않는가
- 정상 흐름과 필수 산출물 실패 흐름이 구분되는가, 기존 팀을 확장했다면 기존 호출도 유지되는가

규모에 맞게 검증하고 구성·경로·검증 결과·미검증·다음 단계를 보고한다. 제작 요청만으로 실제 팀 실행·벤치·배포까지 승인됐다고 보지 않는다.

## 5. 확장·정리

역할 추가 전 기존 역할의 재사용/확장 가능성을 다시 확인한다. 기존 오케스트레이션의 역할 표·입출력·의존성·description을 함께 갱신하고 연결을 검증한다. 안 쓰이는 역할의 병합·삭제·이동은 영향을 알리고 사용자 승인을 받은 뒤 수행한다. 기존 파일을 자동 재배치하지 않는다.
