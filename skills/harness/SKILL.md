# Harness — 서브에이전트 팀 + 오케스트레이션 구축 메타 스킬

비서가 유저의 요청에 적합한 팀이 없을 때, 이 스킬을 참고하여 새 팀을 직접 구축한다.
서브에이전트 정의와 오케스트레이션 스킬을 `Write` 로 생성하고, 비서는 그 오케스트레이션
스킬을 `invoke_skill` 로 로드한 뒤 `Task`(claude) / `spawn_agent`(codex) 로 서브에이전트에게
위임한다.

**실행 모델은 하나**: 서브에이전트 위임 + 파일(`_workspace/`) 데이터 전달. 어느 어댑터로
전환해도 동일하게 동작한다 (핵심원칙 #2). 에이전트 팀·메시지 버스 같은 별도 인프라는 없다.

## 자산 경로 — 헌법 기준 (`<TIGUCLAW_HOME>` 홈 기본, SYSTEM.md §5)

- **서브에이전트**: `<TIGUCLAW_HOME>/agents/<name>.md`
- **오케스트레이션 스킬**: `<TIGUCLAW_HOME>/skills/<orchestrator-name>/SKILL.md`
- **(선택) 슬래시 커맨드**: `<TIGUCLAW_HOME>/commands/<name>.md`
- **프로젝트 전용 자산** (cwd 가 그 프로젝트 폴더일 때만 발견): `<TIGUCLAW_HOME>/workspace/<project>/.tiguclaw/{agents,skills,commands}`

사용자가 명시적으로 "이 레포에"·"이 프로젝트에" 라고 하지 않는 한 **홈이 기본**.

## 워크플로우

### Phase 0: 현황 감사

하네스 스킬이 트리거되면 **가장 먼저 기존 하네스 현황을 확인**한다. 매번 신규 구축으로
가정하면 역할 겹치는 에이전트·스킬이 다른 이름으로 누적된다.

1. user prompt 상단에 자동 prepend 되는 「## 사용 가능 서브에이전트」/「## 사용 가능 스킬」
   인덱스를 읽는다. 더 정확히는 `<TIGUCLAW_HOME>/agents/`, `<TIGUCLAW_HOME>/skills/`
   (프로젝트 작업이면 `<TIGUCLAW_HOME>/workspace/<project>/.tiguclaw/{agents,skills}` 도) 를
   `Glob`/`Read` 로 확인한다.
2. 현황에 따라 실행 모드를 분기한다:

   | 모드 | 진입 조건 | 행동 |
   |------|----------|------|
   | **신규 구축** | 관련 에이전트/스킬이 없음 | Phase 1부터 전체 실행 |
   | **기존 확장** | 관련 하네스가 있고 에이전트/스킬 추가 요청 | 아래 매트릭스대로 필요한 Phase만 |
   | **운영/유지보수** | 감사·수정·동기화 요청 | Phase 7-5 운영 워크플로우로 이동 |

   **기존 확장 시 Phase 선택:**
   | 변경 유형 | Phase 1 | Phase 2 | Phase 3 | Phase 4 | Phase 5 | Phase 6 |
   |----------|---------|---------|---------|---------|---------|---------|
   | 에이전트 추가 | 건너뜀 | 배치만 | 필수 | 전용 스킬 필요 시 | 오케스트레이션 수정 | 필수 |
   | 스킬 추가/수정 | 건너뜀 | 건너뜀 | 건너뜀 | 필수 | 연결 변경 시 | 필수 |
   | 아키텍처 변경 | 건너뜀 | 필수 | 영향 에이전트만 | 영향 스킬만 | 필수 | 필수 |

3. 기존 인덱스와 오케스트레이션 스킬의 구성을 대조해 불일치(drift)를 감지한다.
4. 감사 결과를 사용자에게 요약 보고하고 실행 계획을 확인받는다.

### Phase 1: 도메인 분석

1. 유저 요청에서 도메인/프로젝트 파악
2. 핵심 작업 유형 식별 (설계, 구현, 검증, 분석 등)
3. Phase 0 감사 결과 기반으로 기존 에이전트/스킬과의 충돌·중복 분석
4. 프로젝트 코드베이스 탐색 — `Glob`/`Grep`/`Read` 로 기술 스택·구조 파악
5. **사용자 숙련도 감지** — 대화 맥락(용어·질문 수준)으로 기술 수준을 파악해 톤 조절.
   경험이 적은 사용자에게 "assertion", "JSON schema" 같은 용어를 설명 없이 쓰지 않는다.

### Phase 2: 팀 아키텍처 설계

#### 아키텍처 패턴 선택
| 패턴 | 구조 | 적합한 경우 |
|------|------|-----------|
| **파이프라인** | A→B→C→D | 각 단계가 이전 산출물에 의존 |
| **팬아웃/팬인** | 분배→[A,B,C]→통합 | 독립 병렬 작업 후 통합 |
| **생성-검증** | 생성↔검증 루프 | 품질 기준이 명확한 산출물 |
| **전문가 풀** | 상황별 전문가 선택 | 다양한 유형의 작업 |
| **감독자** | 진행 보고 동적 분배 | 작업량 가변, 런타임 분배 |

> 상세 패턴·복합 패턴·평탄화된 계층 위임: `references/agent-design-patterns.md`

#### 에이전트 분리 기준
4축으로 판단: **전문성**(다른 도메인 지식?)·**병렬성**(독립 수행 가능?)·**컨텍스트**(다른
파일/자료?)·**재사용성**(다른 팀에서도?). 기존 에이전트 중복·재사용 검토는 Phase 3 에서.

### Phase 3: 서브에이전트 정의 생성

#### 3-0. 기존 에이전트 중복 검토
신규 생성 전, 「## 사용 가능 서브에이전트」 인덱스와 대조해 중복을 확인한다. 중복 분류
기준과 재사용 설계는 `references/agent-design-patterns.md` "에이전트 재사용 설계" 참조.

#### 3-1. 정의 작성
각 역할의 서브에이전트 .md 를 `Write` 로 생성한다.

**파일 위치**: `<TIGUCLAW_HOME>/agents/<name>.md` (명시 없으면 홈 기본).
프로젝트 전용일 때만: `<TIGUCLAW_HOME>/workspace/<project>/.tiguclaw/agents/<name>.md`.

**필수**: 에이전트 정의 파일 없이 위임 프롬프트에 역할을 직접 박는 것은 금지. 파일로
존재해야 다음 세션 재사용 + 자동 발견 인덱스 등록이 된다.

**모델 등급 (핵심원칙 #2 — 하드코딩 금지)**: `model:` 은 특정 모델명이 아니라 **등급**으로.
- `high` — 추론 품질이 결과를 좌우하는 핵심 역할 (설계·통합·검증)
- `mid` — 일반 구현·분석
- `low` — 단순·반복·대량 (요약·추출·포맷)

등급은 어댑터가 자기 풀로 해석한다 (codex=`MODEL_TIER_*` 풀, claude=high→opus/mid→sonnet
/low→haiku). `model: "opus"` 처럼 박으면 어댑터마다 동작이 갈려 #2 위반이다.

**도구**: 최소한만 부여 (설계자에게 `Write`/`Edit` X). 정의 구조·도구 가이드는
`references/agent-design-patterns.md` "에이전트 정의 구조" 참조.

**QA 에이전트 포함 시**: QA 의 핵심은 "존재 확인"이 아니라 **경계면 교차 비교**. 전체
완성 후 1회가 아니라 각 모듈 완성 직후 점진 실행. 상세: `references/qa-agent-guide.md`.

### Phase 4: 스킬 생성 — skill-creator 에 위임

팀이 어떤 스킬을 필요로 하는지(각 서브에이전트용 or 비서 직접용)는 여기서 정하되, **개별 스킬을 실제로 작성하는 방법은 `skill-creator` 스킬을 따른다** — 개별 스킬 작성의 단일 정식 경로다. SKILL.md 규격·description 작성 원칙(pushy 트리거)·progressive disclosure·위치 규칙의 진실 소스는 `skill-creator/references/skill-format.md`. 여기에 중복 서술하지 않는다(둘로 갈라지면 drift).

- **무엇을 만들지(harness 몫)**: Phase 2 아키텍처에서 도출된, 이 팀에 필요한 스킬 목록. 먼저 「## 사용 가능 스킬」 인덱스와 대조해 중복을 피한다.
- **어떻게 만들지(skill-creator 몫)**: 각 스킬을 skill-creator 의 **기본 경로**(의도 → 초안 → 빠른 정성 확인 → human-gate)로 작성. 팀 스킬 여러 개를 각각 무겁게 벤치하지 마라 — skill-creator 의 정량 eval 은 그 스킬이 중요/논쟁적일 때만 opt-in.

### Phase 5: 오케스트레이션 스킬 생성

tiguclaw 의 단위는 **에이전트 + 스킬** (별도 "team" 파일 개념 없음). 팀 = 여러 서브에이전트
정의 + 1개의 오케스트레이션 스킬. 이 스킬이 "누가 언제 어떤 순서로 협업하는가" 를 묶는다.

**위치**: `<TIGUCLAW_HOME>/skills/<팀이름>/SKILL.md` (또는 프로젝트 전용 시 워크스페이스
하위). **팀 이름 규칙**: `도메인-목적` (예: web-dashboard, game-rpg, data-pipeline).

오케스트레이션 SKILL.md 를 `Write` 로 생성한다. 작업 유형별(새 Phase / 버그 수정 / 설계
검토) 위임 방법, 각 서브에이전트 이름·산출물 경로·빌드 명령 등 구체적 실행 컨텍스트를 담는다.

> 전체 템플릿·데이터 전달·에러 핸들링·후속 작업 지원: `references/orchestrator-template.md`

**기존 확장 시**: 오케스트레이션 스킬을 새로 만들지 말고 기존 것을 수정한다. 새 에이전트를
구성·데이터 흐름에 반영하고, description 에 관련 트리거 키워드를 추가한다.

**변경 이력 위치 (tiguclaw 규칙)**: tiguclaw 는 `CLAUDE.md` 를 비서 런타임 포인터로 쓰지
않고(개발 레포 CLAUDE.md 는 자체 개발용), SYSTEM.md 는 불변(§3)이라 거기에도 안 쓴다.
대신 **트리거는 오케스트레이션 스킬 description 의 자동 발견이 대체**(별도 포인터 불필요),
**변경 이력은 오케스트레이션 스킬 본문 끝 `## 변경 이력` 테이블**에 둔다.

### Phase 6: 검증 + 완료 보고

체크리스트:
- [ ] 모든 서브에이전트 파일이 `<TIGUCLAW_HOME>/agents/` (또는 프로젝트 워크스페이스) 에 존재
- [ ] 오케스트레이션 스킬이 `<TIGUCLAW_HOME>/skills/<팀이름>/SKILL.md` 에 존재
- [ ] 각 에이전트 frontmatter(name, description) + tools 가 역할에 적합, model 은 등급(high/mid/low)
- [ ] 오케스트레이션 SKILL.md 가 참조하는 에이전트 이름이 실제 파일과 일치
- [ ] 산출물 경로는 절대 경로로 명시 (`_workspace/` 기준)
- [ ] 스킬 description 이 적극적("pushy") + 후속 작업 키워드 포함
- [ ] SKILL.md 본문 500줄 이내 (초과 시 references/ 분리)
- [ ] 커맨드를 의도치 않게 생성하지 않음
- [ ] 트리거 검증 통과 (아래 "테스트 방법론")

검증 통과 후 비서는 유저에게 **하네스 구성 결과를 반드시 보고**한다 (팀 이름·파이프라인·
에이전트 표[에이전트/역할/도구/핵심 제약]·산출물 경로·다음 단계 제안).

#### 테스트 방법론 (요약)

생성한 하네스를 다음으로 검증한다. 상세는 `references/orchestrator-template.md` 참조.

1. **구조 검증** — 에이전트/스킬 파일 위치, frontmatter(name·description), 에이전트↔스킬
   참조 일관성, 커맨드 미생성 확인.
2. **트리거 검증** — 각 스킬 description 에 대해:
   - **should-trigger** (8~10개) — 트리거해야 하는 다양한 표현 (공식적/캐주얼, 명시/암시)
   - **should-NOT-trigger** (8~10개) — 키워드는 유사하나 다른 도구/스킬이 적합한 "near-miss".
     명백히 무관한 쿼리("피보나치 작성")는 가치 없음 — **경계가 모호한** 쿼리가 좋은 케이스.
   - 기존 스킬과의 트리거 충돌도 이 단계에서 확인.
3. **드라이런** — 오케스트레이션 Phase 순서가 논리적인지, 데이터 전달 경로에 빈 구간(dead
   link)이 없는지(각 서브에이전트 입력이 이전 Phase 출력과 매칭), 에러 시나리오 폴백이
   실행 가능한지 검토.
4. **(선택) 실행 테스트** — 현실적 테스트 프롬프트 2~3개로 실제 위임 검증. 산출물이 객관
   검증 가능하면 assertion, 주관적이면 사용자 피드백으로 평가. 문제 발견 시 피드백을
   **일반화**해 수정(좁은 수정 금지) 후 재테스트.

### Phase 7: 하네스 진화

하네스는 한 번 만들고 끝나는 정적 산출물이 아니라, 피드백에 따라 계속 진화하는 시스템이다.

#### 7-1. 실행 후 피드백 수집
매 실행 완료 후 사용자에게 기회를 제공한다 (강요 X): "결과에서 개선할 부분이 있나요?",
"팀 구성이나 워크플로우에 바꾸고 싶은 점이 있나요?" 피드백이 없으면 넘어간다.

#### 7-2. 피드백 반영 경로
| 피드백 유형 | 수정 대상 | 예시 |
|-----------|----------|------|
| 결과물 품질 | 해당 에이전트의 스킬 | "분석이 피상적" → 스킬에 깊이 기준 추가 |
| 에이전트 역할 | 에이전트 정의 .md | "보안 검토 필요" → 새 에이전트 추가 |
| 워크플로우 순서 | 오케스트레이션 스킬 | "검증을 먼저" → Phase 순서 변경 |
| 팀 구성 | 오케스트레이션 + 에이전트 | "둘은 합쳐도 될 듯" → 에이전트 병합 |
| 트리거 누락 | 스킬 description | "이 표현으로 작동 안 함" → description 확장 |

#### 7-3. 변경 이력
모든 변경은 **오케스트레이션 스킬 본문 끝 `## 변경 이력` 테이블**에 기록한다 (날짜·변경
내용·대상·사유). 이 이력으로 진화 방향을 추적하고 퇴행을 방지한다.
(`references/orchestrator-template.md` "변경 이력" 참조.)

#### 7-4. 진화 트리거
"하네스 수정해줘" 명시 요청 외에도 다음 상황에서 진화를 **제안**한다:
- 같은 유형 피드백이 2회 이상 반복
- 에이전트가 반복적으로 실패하는 패턴 발견
- 사용자가 오케스트레이션을 우회해 수동 작업하는 것이 관찰됨

#### 7-5. 운영/유지보수 워크플로우
Phase 0 에서 "운영/유지보수" 분기로 진입했을 때 따른다.

1. **현황 감사** — `<TIGUCLAW_HOME>/agents/`·`skills/` 목록과 오케스트레이션 스킬 구성을
   대조해 불일치 목록 생성 → 사용자에게 보고.
2. **점진 추가/수정** — 한 번에 하나씩 변경, 각 변경 후 즉시 동기화.
3. **변경 이력 갱신** — 오케스트레이션 스킬의 `## 변경 이력` 에 날짜·내용·대상·사유 기록.
4. **변경 검증** — 구조 검증(Phase 6), 트리거 영향 시 트리거 검증, 대규모 변경 시 드라이런까지.
   오케스트레이션 스킬과 실제 파일의 일치를 최종 확인.

## 핵심 — 비서는 직접 작업하지 않는다

- 하네스로 구성된 팀을 쓰는 모든 작업은 **반드시 서브에이전트에게 위임**한다.
- 비서의 역할은 오케스트레이션(위임·수신·판단·보고)만. 설계는 designer 에게, 구현은
  implementer 에게, 검증은 qa 에게.
- 비서가 직접 코드 작성·파일 수정·빌드 실행하면 팀 구성의 목적을 무너뜨린다.

## 원칙

- 에이전트는 **역할이 명확**해야 한다 (하나의 역할에 집중 = 재사용성↑)
- 도구는 **최소한만**, model 은 **등급(high/mid/low)** 으로 (특정 모델명 하드코딩 금지 = #2)
- 파이프라인은 **단방향**이 기본. 복잡한 루프는 오케스트레이션에서 비서가 판단
- 오케스트레이션은 **시스템이 아닌 .md** 로 정의한다
- 중간 산출물은 `_workspace/` 에 보존 (삭제하지 않음 — 사후 검증/감사 추적)
- 새 자산은 **홈이 기본** (SYSTEM.md §5) — "이 레포에/이 프로젝트에" 명시 시에만 워크스페이스

## ★ 오케스트레이트 게이트 (팀 크기보다 먼저)

팀을 만들지 **말지**가 팀 크기보다 앞선 결정이다. 오케스트레이션은 공짜가 아니다 —
**서브에이전트 위임은 단일 실행 대비 대략 5배 토큰**을 쓴다(각 에이전트가 컨텍스트를
새로 싣는다). 그러니 먼저 통과:

- **팀으로 갈 때**: 서로 **독립·비중첩**인 하위작업이 **3개 이상**이고 각각 솔로로 상당한
  시간이 걸릴 때. 팬아웃의 병렬 이점이 5배 토큰·조율 비용을 넘는 경우.
- **솔로/직접으로 갈 때**: 단일 파일·단일 모듈 작업, audit-only, 읽고 답하는 질의, 하위작업이
  긴밀히 얽혀(순차 의존) 병렬 이점이 없는 경우 → `Task`/`spawn_agent` 1명 또는 비서가 직접.
  **팀 구성 자체가 낭비다.**

Anthropic 도 같은 원칙: *"단순 해법이 부족할 때만 멀티스텝 에이전트를 추가하라."* 낭비 없는
오케스트레이션의 첫 규칙은 "필요 없으면 오케스트레이트하지 않는다"이다.

## 팀 크기 가이드라인 (게이트 통과 후)

| 작업 규모 | 권장 팀원 수 | 이유 |
|----------|------------|------|
| 소규모 (5~10개 작업) | 2~3명 | 조율 오버헤드 최소 |
| 중규모 (10~20개 작업) | 3~5명 | 병렬 처리 이점 |
| 대규모 (20개+ 작업) | 5~7명 | 7명 초과는 조율 비용이 이점 초과 |

> 3명의 집중된 팀원이 5명의 산만한 팀원보다 낫다.
