# 서브에이전트 팀 설계 패턴

tiguclaw 의 하네스는 **서브에이전트 + 오케스트레이션 스킬**로 구성된다.
"에이전트 팀"(팀원끼리 직접 통신하는 별도 런타임)은 tiguclaw 에 **없다** — 대신
비서가 오케스트레이션 스킬을 로드한 뒤 서브에이전트에게 위임하고, 서브에이전트
간 데이터는 파일(`_workspace/`)로 전달한다.

## 목차

1. 실행 모델 (서브에이전트 위임 + 파일 전달)
2. 아키텍처 패턴 6종
3. 복합 패턴
4. 에이전트 분리 기준
5. 에이전트 재사용 설계
6. 에이전트 정의 구조
7. 스킬 vs 에이전트 구분

---

## 1. 실행 모델 — 서브에이전트 위임 + 파일 전달

tiguclaw 의 유일한 실행 모델은 **서브에이전트 위임**이다.

```
[비서] ── invoke_skill("팀이름") ──→ 오케스트레이션 스킬 로드
   │
   ├── spawn_agent(name, prompt) (세 어댑터 공통 MCP 도구)
   ├── spawn_agent({name, prompt}) (codex 어댑터: spawn_agent MCP 도구)
   │
   └── 서브에이전트가 산출물을 `_workspace/{phase}_{agent}_{artifact}.md` 에 기록
       → 다음 서브에이전트가 그 파일을 Read 로 읽어 이어받음
```

**핵심 도구 (어댑터별 위임 — 동작 동등):**
- 세 어댑터 공통 → `spawn_agent` (우리 루프에서 실행 — 관측·스티어·취소 가능)
- codex 어댑터 → `spawn_agent({name, prompt})` (MCP 도구)

비서는 매 턴 작동 컨텍스트에 자동으로 실리는 「## 사용 가능 서브에이전트」 인덱스에서
서브에이전트를 발견한다. 어느 어댑터로 전환해도 동일하게 동작한다 (핵심원칙 #2).

**서브에이전트 간 통신은 파일 기반.** 서브에이전트끼리 메시지를 주고받는 메커니즘은
없다. 한 서브에이전트의 산출물을 다른 서브에이전트가 읽어야 하면, 오케스트레이션
스킬이 **파일 경로를 양쪽 프롬프트에 명시**한다.

**깊이 제한 (재귀 위임 불가):** 서브에이전트는 `subagentDepth: 1` 로 실행되어
**자체적으로 다시 서브에이전트를 spawn 할 수 없다.** 따라서 모든 위임은 비서(depth 0)
→ 서브에이전트(depth 1) 단일 계층이다. "계층적 위임" 패턴(아래 6번)은 이 제약 때문에
**오케스트레이션 스킬 안에서 비서가 단계를 나눠 평탄화**해 구현한다.

**왜 이 모델인가:** tiguclaw 코어는 마이크로커널이다. 팀 통신 인프라(메시지 버스·공유
작업 목록)를 코어에 박는 대신, 능력을 데이터(.md + 파일)로 확장한다. 파일 기반 전달은
대용량 산출물·감사 추적·재실행에 강하고, 어댑터에 독립적이다.

## 2. 아키텍처 패턴 6종

| 패턴 | 구조 | 적합한 경우 |
|------|------|-----------|
| **파이프라인** | A→B→C→D | 각 단계가 이전 산출물에 강하게 의존 |
| **팬아웃/팬인** | 분배→[A,B,C]→통합 | 독립적 병렬 작업 후 통합 |
| **전문가 풀** | 라우터→{A\|B\|C} | 입력 유형에 따라 다른 처리 |
| **생성-검증** | 생성↔검증 루프 | 품질 기준이 명확한 산출물 |
| **감독자** | 감독자가 상태 보고 동적 분배 | 작업량이 가변적, 런타임 분배 |
| **계층적 위임 (평탄화)** | 비서가 단계 분해 | 문제가 자연스럽게 계층 분해됨 |

### 2-1. 파이프라인 (Pipeline)
순차 작업. 이전 서브에이전트의 출력 파일이 다음 서브에이전트의 입력.
```
[분석] → [설계] → [구현] → [검증]
```
예: 소설 집필 — 세계관 → 캐릭터 → 플롯 → 집필 → 편집.
주의: 병목이 전체를 지연시킨다. 각 단계를 가능한 독립적으로.

### 2-2. 팬아웃/팬인 (Fan-out/Fan-in)
독립 작업을 병렬 위임 후 통합. tiguclaw 에서 가장 효율적인 패턴.
```
         ┌→ [전문가A] → 02_A.md ─┐
[비서] → ├→ [전문가B] → 02_B.md ─┼→ [통합: Read 후 종합]
         └→ [전문가C] → 02_C.md ─┘
```
병렬 위임은 단일 메시지에서 `spawn_agent` 을 여러 개 동시 호출(
codex `spawn_agent` 다중). 각 서브에이전트는 독립 산출물을 `_workspace/` 에 기록.
주의: 통합 단계의 품질이 전체 품질을 결정.

### 2-3. 전문가 풀 (Expert Pool)
입력 유형에 따라 적합한 전문가만 선택 위임.
```
[라우터(비서)] → { 전문가A | 전문가B | 전문가C }
```
예: 코드 리뷰 — 보안/성능/아키텍처 중 해당 영역만 위임. 라우터(비서)의 분류 정확도가 핵심.

### 2-4. 생성-검증 (Producer-Reviewer)
생성 서브에이전트와 검증 서브에이전트가 쌍으로 동작.
```
[생성] → 산출물.md → [검증] → (문제 시) → [생성] 재위임
```
서브에이전트 간 직접 피드백은 불가하므로, **비서가 검증 결과를 읽고 생성
서브에이전트에게 재위임**한다. 무한 루프 방지를 위해 최대 재시도(2~3회) 설정 필수.

### 2-5. 감독자 (Supervisor)
비서가 작업 상태 파일을 보며 워커 서브에이전트에게 동적으로 배치 할당.
```
         ┌→ [워커A]
[비서] ─┼→ [워커B]   ← 비서가 진행 파일을 보고 다음 배치 위임
         └→ [워커C]
```
팬아웃과의 차이: 팬아웃은 사전 고정 분배, 감독자는 진행을 보며 동적 조정.
예: 대규모 코드 마이그레이션 — 비서가 파일 목록을 배치로 나눠 순차 위임.

### 2-6. 계층적 위임 (평탄화)
문제가 계층적으로 분해되는 구조. 서브에이전트는 재귀 spawn 불가(depth 1)이므로,
**비서가 오케스트레이션 스킬 안에서 단계를 평탄화**해 구현한다.
```
[비서] → 1단계: [팀장역 분석가] → 하위 작업 목록 파일 산출
        2단계: 비서가 그 목록대로 [실무자1], [실무자2] … 직접 위임
```
즉 "팀장이 실무자를 spawn"하는 게 아니라, "팀장역이 분해 계획을 파일로 내고,
비서가 그 계획대로 실무자를 위임"한다. 깊이 2단계 이내 권장.

## 3. 복합 패턴

실전에서는 단일 패턴보다 복합이 흔하다.

| 복합 패턴 | 구성 | 예시 |
|----------|------|------|
| **팬아웃 + 생성-검증** | 병렬 생성 후 각각 검증 | 다국어 번역 — 4개 병렬 번역 → 각각 리뷰 |
| **파이프라인 + 팬아웃** | 순차 중 일부 병렬화 | 분석(순차)→구현(병렬)→통합테스트(순차) |
| **감독자 + 전문가 풀** | 비서가 분류 후 전문가 동적 위임 | 문의 처리 — 분류 후 적합 전문가 할당 |

복합 패턴에서도 실행 모델은 동일하다: 비서가 위임하고, 데이터는 `_workspace/` 파일로
흐른다. Phase 경계에서 산출물 파일 경로가 다음 Phase 서브에이전트의 입력으로
연결되는지 오케스트레이션 스킬에 명시한다.

## 4. 에이전트 분리 기준

전문성·병렬성·컨텍스트·재사용성 4축으로 판단한다.

| 기준 | 분리 | 통합 |
|------|------|------|
| 전문성 | 영역이 다르면 분리 | 영역이 겹치면 통합 |
| 병렬성 | 독립 실행 가능하면 분리 | 순차 종속이면 통합 고려 |
| 컨텍스트 | 컨텍스트 부담이 크면 분리 | 가볍고 빠르면 통합 |
| 재사용성 | 다른 팀에서도 쓰면 분리 | 이 팀에서만 쓰면 통합 고려 |

원칙: 하나의 에이전트가 하나의 역할에 집중할수록 재사용성이 높고 중복이 줄어든다.
역할이 둘 이상이면 분리할 수 있는지 먼저 검토한다.

## 5. 에이전트 재사용 설계

신규 서브에이전트 생성 전, 기존 에이전트와의 중복을 확인한다. 매 턴 작동 컨텍스트에
자동으로 실리는 「## 사용 가능 서브에이전트」 인덱스를 먼저 본다(중복 방지).

| 상황 | 조치 |
|------|------|
| 기존 에이전트가 신규 역할을 완전히 포함 | 신규 생성 금지 — 기존 재사용 |
| 기존이 부분 포함이고 일반화 가능 | 기존을 일반화하여 확장 |
| 도메인 특화가 의도된 부분 포함 | 신규 생성 진행 — 별개로 유지 |
| 역할 범위가 완전히 다름 | 신규 생성 진행 |

기존 에이전트 일반화 시: 그 에이전트에 의존하는 오케스트레이션 스킬의 동작이 바뀔 수
있다. 확장 전 의존성을 확인하고, 일반화 후 드라이런으로 기존 동작 유지를 확인한다.

## 6. 에이전트 정의 구조

모든 서브에이전트는 `.md` 파일로 정의한다. 파일 없이 위임 프롬프트에 역할을 직접
박는 것은 금지 — 파일로 존재해야 다음 세션에서 재사용 가능하고, 자동 발견(`discoverAgents`)
인덱스에 올라간다.

**위치 (SYSTEM.md §5 — 홈이 기본):**
- 공통: `<TIGUCLAW_HOME>/agents/<name>.md`
- 프로젝트 전용 (cwd 가 그 폴더일 때만 발견): `<TIGUCLAW_HOME>/workspace/<project>/agents/<name>.md`

사용자가 "이 레포에"·"이 프로젝트에" 라고 명시하지 않으면 **홈이 기본**.

```markdown
---
name: agent-name
description: "1-2문장 역할 설명 + 위임 트리거 키워드."
model: high          # 등급: high / mid / low (아래 '모델 등급' 참조). 생략 시 어댑터 디폴트.
tools:               # 콤마 구분. 생략 시 전체 도구. "none" 이면 도구 0.
  - Read
  - Grep
  - Glob
---

# Agent Name — 역할 한줄 요약

당신은 [도메인]의 [역할] 전문가입니다.

## 핵심 역할
1. 역할1
2. 역할2

## 작업 원칙
- 원칙1

## 입력/출력 프로토콜
- 입력: [어떤 _workspace/ 파일을 Read 하는지]
- 출력: [어느 _workspace/ 경로에 무엇을 Write 하는지]
- 형식: [파일 포맷, 구조]

## 에러 핸들링
- [실패/막힘 시 행동 — 비서에게 무엇을 보고하는지]

## 재호출 시 행동
- 이전 산출물 파일이 있으면 Read 후 개선점 반영
- 사용자 피드백이 주어지면 해당 부분만 수정

## 협업
- 어느 에이전트의 산출물을 입력으로 받고, 누구의 입력이 되는지
```

**모델 등급 (핵심원칙 #2 — 하드코딩 금지):**
서브에이전트의 `model:` 은 특정 모델명이 아니라 **등급**으로 쓴다. 등급은 어댑터가
자기 풀로 해석한다 — codex 는 `MODEL_TIER_*` 콤마 풀, claude 는 대표 모델(high→opus
/ mid→sonnet / low→haiku)로 매핑. `model: "opus"` 처럼 특정 모델을 박으면 다른
어댑터에서 동작이 갈려 #2 위반이다.

| 등급 | 언제 | 의미 |
|------|------|------|
| `high` | 추론 품질이 결과를 좌우하는 핵심 역할 (설계·통합·검증) | 최상위 풀 |
| `mid` | 일반 구현·분석 | 중간 풀 |
| `low` | 단순·반복·대량 (요약·추출·포맷) | 경량 풀 |

`tools: none` 인 단순작업 서브에이전트는 장기기억 주입도 생략된다(lean). 도구는
**최소한만** 부여 — 설계자에게 `Write`/`Edit` 을 주지 않는다.

**도구 선택 가이드 (tiguclaw 표준 도구명):**

| 역할 유형 | 권장 도구 |
|----------|----------|
| 분석/설계 (읽기 전용) | `Read`, `Grep`, `Glob` |
| 구현 (쓰기 가능) | `Read`, `Write`, `Edit`, `Grep`, `Glob`, `Bash` |
| 검증/QA | `Read`, `Grep`, `Bash` (테스트·빌드 실행) |
| 리서치 | `Read`, `Grep`, `WebSearch`, `WebFetch` |

## 7. 스킬 vs 에이전트 구분

| 구분 | 스킬 (Skill) | 에이전트 (Agent) |
|------|-------------|-----------------|
| 정의 | 절차적 지식 (워크플로우) | 전문가 페르소나 + 행동 원칙 |
| 위치 | `<TIGUCLAW_HOME>/skills/<name>/SKILL.md` | `<TIGUCLAW_HOME>/agents/<name>.md` |
| 트리거 | description 키워드 매칭 (자동 발견) | 비서가 `spawn_agent` 으로 명시 위임 |
| 용도 | "어떻게 하는가" | "누가 하는가" |

스킬은 절차적 가이드, 에이전트는 그 가이드를 수행하는 전문가 역할 정의다.
오케스트레이션 스킬은 "누가 언제 어떤 순서로" 를 묶는 스킬의 특수 형태다.
