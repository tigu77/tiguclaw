# 오케스트레이션 스킬 템플릿

오케스트레이션 스킬은 서브에이전트 팀을 하나의 워크플로우로 묶는 스킬이다.
비서는 이 스킬을 `invoke_skill("팀이름")` 으로 로드한 뒤, 본문에 적힌 위임 패턴대로
`spawn_agent` 으로 서브에이전트에게 작업을 위임한다.

실행 모델은 하나뿐이다 — **서브에이전트 위임 + 파일(`_workspace/`) 데이터 전달**.
(에이전트 팀·메시지 버스·공유 작업 목록 같은 별도 인프라는 tiguclaw 에 없다.)

## 목차

1. 표준 템플릿
2. 컨텍스트 확인 (Phase 0 — 초기/후속/부분 재실행)
3. 데이터 전달 프로토콜
4. 에러 핸들링
5. description 작성 (후속 작업 키워드)
6. 변경 이력 (오케스트레이션 스킬 안에 둔다)
7. 작성 원칙

---

## 1. 표준 템플릿

```markdown
---
name: {domain}-orchestrator
description: "{도메인} 서브에이전트 팀을 조율하는 오케스트레이션 스킬. {초기 실행 키워드}. 후속 작업: {도메인} 결과 수정, 부분 재실행, 업데이트, 보완, 다시 실행, 이전 결과 개선 요청 시에도 이 스킬을 사용."
---

# {Domain} Orchestration

{도메인}의 서브에이전트 팀을 조율하여 {최종 산출물}을 생성하는 통합 스킬.

## 구성 멤버 (서브에이전트)

| 서브에이전트 | model 등급 | 역할 | 입력 | 출력 |
|-------------|-----------|------|------|------|
| {agent-1} | high | {역할} | {입력 파일/소스} | `_workspace/{phase}_{agent-1}_{artifact}.md` |
| {agent-2} | mid  | {역할} | {앞 단계 산출물} | `_workspace/{phase}_{agent-2}_{artifact}.md` |
| {qa}      | high | 검증 | {대상 파일들} | `_workspace/{phase}_{qa}_report.md` |

## 작업 분류
요청을 분류하여 진행 방식 결정:
- A. {유형1 — 예: 신규 전체} → 전체 파이프라인
- B. {유형2 — 예: 부분 수정} → 해당 서브에이전트만 재위임

## 워크플로우

### Phase 0: 컨텍스트 확인 (후속 작업 지원)
1. `<작업폴더>/_workspace/` 존재 여부 확인
2. 모드 결정:
   - 미존재 → 초기 실행 (Phase 1)
   - 존재 + 부분 수정 요청 → 부분 재실행 (해당 서브에이전트만, 이전 산출물 경로를 프롬프트에 포함)
   - 존재 + 새 입력 → 새 실행 (기존 `_workspace/` 를 `_workspace_{YYYYMMDD_HHMMSS}/` 로 이동 후 재생성)

### Phase 1: 준비
1. 입력 분석 — {무엇을 파악}
2. `_workspace/` 생성, 입력을 `_workspace/00_input/` 에 저장

### Phase 2: {주요 작업 — 위임}
비서가 서브에이전트에게 위임 (`spawn_agent`):
- 병렬 가능한 작업은 단일 메시지에서 동시 위임
- 각 서브에이전트 프롬프트에 **입력 파일 경로**와 **출력 파일 경로**를 절대 경로로 명시
- {agent-1} → {agent-2} 의존이면, {agent-1} 산출물 경로를 {agent-2} 프롬프트에 명시

### Phase 3: 통합/검증
1. 각 서브에이전트 산출물을 Read 로 수집
2. {qa} 서브에이전트에게 교차 검증 위임 (대상 파일 경로 명시)
3. 최종 산출물 생성: `{output-path}/{filename}`

### Phase 4: 정리 + 보고
1. `_workspace/` 보존 (중간 산출물 삭제 X — 사후 검증·감사 추적)
2. 사용자에게 결과 요약 보고 (서브에이전트 출력을 그대로 흘리지 말고 비서 인격으로 정리)

## 데이터 흐름
[비서] → 위임 → [agent-1] → 01_agent-1.md ┐
              → [agent-2] → 02_agent-2.md ┼→ [비서: Read + 통합] → 최종 산출물
                                           ┘   → [qa] → report.md

## 에러 핸들링
- 서브에이전트 1개 실패: 1회 재위임. 재실패 시 누락 명시하고 진행
- 과반 실패: 사용자에게 알리고 진행 여부 확인
- 생성-검증 루프: 최대 2~3회. 초과 시 사용자에게 에스컬레이션
- 산출물 충돌: 출처 병기, 삭제하지 않음

## 테스트 시나리오
- 정상 흐름 1개 + 에러 흐름 1개 이상 기술

## 변경 이력
| 날짜 | 변경 내용 | 대상 | 사유 |
|------|----------|------|------|
| {YYYY-MM-DD} | 초기 구성 | 전체 | - |
```

## 2. 컨텍스트 확인 (Phase 0)

오케스트레이션 스킬은 초기 실행뿐 아니라 후속 작업도 처리해야 한다. `_workspace/`
존재 여부로 모드를 가른다:

- **미존재** → 초기 실행
- **존재 + 부분 수정 요청** → 부분 재실행. 해당 서브에이전트만 재위임하고, 이전
  산출물 경로를 그 서브에이전트 프롬프트에 포함해 "기존 결과를 읽고 피드백을 반영"
  하도록 지시 (에이전트 정의의 「재호출 시 행동」 섹션과 호응)
- **존재 + 새 입력** → 새 실행. 기존 `_workspace/` 를 `_workspace_{타임스탬프}/` 로
  이동한 뒤 새로 시작

후속 작업을 지원하지 않으면 하네스는 첫 실행 후 사실상 죽은 코드가 된다.

---

## 3. 데이터 전달 프로토콜

tiguclaw 의 서브에이전트 간 전달은 **파일 기반이 유일**하다 (메시지 버스 없음).

| 방식 | 구현 | 적합한 경우 |
|------|------|-----------|
| **파일 기반** | 약속된 `_workspace/` 경로에 Write → 다음 에이전트가 Read | 모든 중간 산출물 (기본) |
| **반환값 기반** | 위임 도구의 반환 텍스트를 비서가 직접 수집 | 짧은 결과·요약을 비서가 즉시 통합 |

규칙:
- 작업 폴더 하위 `_workspace/` 에 중간 산출물 저장
- 파일명: `{phase}_{agent}_{artifact}.{ext}` (예: `01_analyst_requirements.md`)
- 경로는 **절대 경로**로 프롬프트에 명시 (상대 경로 금지)
- 최종 산출물만 사용자 지정 경로에 출력, 중간 파일은 보존
- 프로젝트 전용 작업은 `<TIGUCLAW_HOME>/workspace/<project>/_workspace/` 하위 (SYSTEM.md §5)

---

## 4. 에러 핸들링

핵심 원칙: **1회 재시도 후 재실패 시 그 결과 없이 진행(보고서에 누락 명시),
상충 데이터는 삭제하지 않고 출처 병기.**

| 상황 | 전략 |
|------|------|
| 서브에이전트 1개 실패 | 1회 재위임 → 재실패 시 누락 명시하고 진행 |
| 과반 실패 | 사용자에게 알리고 진행 여부 확인 |
| 타임아웃/긴 작업 | 무거우면 `run_in_background` 워커에 위임(SYSTEM.md §1) |
| 생성-검증 무한 루프 | 최대 2~3회 재시도 후 사용자 에스컬레이션 |
| 산출물 충돌 | 출처 병기, 삭제 금지 |
| 파괴적 작업 필요 | 비서가 실행 전 사용자 명시 승인 (SYSTEM.md §1) |

## 5. description 작성 — 후속 작업 키워드

오케스트레이션 스킬의 description 이 **유일한 트리거 메커니즘**이다(자동 발견
`discoverSkills` 가 description 을 인덱스에 올린다). 초기 실행 키워드만으로는 후속
요청이 트리거되지 않으니, 다음을 반드시 포함한다:

- 재실행 / 다시 실행 / 업데이트 / 수정 / 보완
- "{도메인}의 {부분}만 다시"
- "이전 결과 기반으로", "결과 개선"
- 도메인 관련 일상 요청 (예: 런치 전략 팀이면 "런치", "홍보", "트렌딩")

---

## 6. 변경 이력 — 오케스트레이션 스킬 안에 둔다

tiguclaw 는 `CLAUDE.md` 를 비서 런타임 포인터로 쓰지 **않는다.** (개발 레포의
`CLAUDE.md` 는 tiguclaw 자체 개발용이다.) 그리고 SYSTEM.md 는 불변(자율 수정 금지,
§3)이라 거기에도 쓰지 않는다.

대신:
- **트리거 등록은 불필요** — 오케스트레이션 스킬의 description 이 자동 발견되어
  트리거 역할을 한다 (별도 포인터 파일 없음).
- **변경 이력은 오케스트레이션 스킬 본문 끝의 `## 변경 이력` 테이블**에 둔다.
  프로젝트 전용 팀이면 그 워크스페이스(`<TIGUCLAW_HOME>/workspace/<project>/skills/
  <팀이름>/SKILL.md`) 안에 둔다.

```markdown
## 변경 이력
| 날짜 | 변경 내용 | 대상 | 사유 |
|------|----------|------|------|
| 2026-06-19 | 초기 구성 | 전체 | - |
| 2026-06-21 | QA 에이전트 추가 | agents/qa.md | 통합 정합성 검증 부족 |
| 2026-06-24 | 톤 가이드 추가 | skills/content-creator | "너무 딱딱하다" 피드백 |
```

이 이력으로 하네스가 어떻게 진화했는지 추적하고 퇴행(regression)을 방지한다.

---

## 7. 작성 원칙

1. **파일 경로는 절대적으로** — 상대 경로 금지, `_workspace/` 기준 명확한 경로
2. **위임 파라미터 완전 명시** — name, prompt, (필요 시 model 등급), 입력·출력 경로
3. **Phase 간 의존성 명시** — 어느 Phase 가 어느 Phase 산출물에 의존하는지
4. **에러 핸들링은 현실적으로** — "모두 성공한다" 가정 금지
5. **테스트 시나리오 필수** — 정상 1 + 에러 1 이상
6. **비서는 직접 작업하지 않는다** — 팀이 구성된 이상 실행은 항상 서브에이전트에게.
   비서의 역할은 오케스트레이션(위임·수신·판단·보고)만.
