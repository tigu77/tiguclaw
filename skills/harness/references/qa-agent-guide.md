# QA 에이전트 설계 가이드

빌드 하네스에 QA 서브에이전트를 포함할 때 참고한다. 실제 프로젝트에서 반복 발견된
**경계면 결함** 패턴과 근본 원인을 바탕으로, QA 가 놓치기 쉬운 결함을 체계적으로
잡는 검증 방법론을 제공한다.

## 목차

1. QA 가 놓치는 결함의 패턴 (경계면 불일치)
2. 통합 정합성 검증 (교차 비교)
3. QA 에이전트 설계 원칙
4. QA 에이전트 정의 템플릿

---

## 1. QA 가 놓치는 결함의 패턴 — 경계면 불일치

가장 빈번한 결함. 두 컴포넌트가 각각 "올바르게" 구현되어 있지만, **연결 지점에서
계약(contract)이 어긋난다.** 각각 개별로는 정상이라 단독 검증으로는 안 잡힌다.

| 경계면 | 불일치 예시 | 놓치는 이유 |
|--------|-----------|-----------|
| API 응답 → 클라이언트 | API 가 `{ items: [...] }` 반환, 호출측은 배열 기대 | 각각 검증하면 정상, 교차 비교 안 함 |
| 필드명 표기 | 생산자 `thumbnailUrl`(camel), 소비자 `thumbnail_url`(snake) | 캐스팅·제네릭이 컴파일러를 통과시킴 |
| 파일 경로 → 링크 | 페이지가 `/dashboard/create` 인데 링크가 `/create` | 파일 구조와 링크를 교차 안 함 |
| 상태 전이 → 실제 업데이트 | 전이 맵에 정의됐는데 코드에서 전환 누락 | 맵 존재만 확인, 업데이트 코드 미추적 |
| 엔드포인트 → 호출부 | API 존재하지만 부르는 곳 없음 | 엔드포인트 목록과 호출 목록 1:1 매핑 안 함 |
| 즉시 응답 → 비동기 결과 | API 가 즉시 `{status}` 반환, 소비자가 최종 결과 필드 접근 | 동기/비동기 응답 구분 없이 타입만 확인 |

**왜 정적 리뷰·빌드 통과로 못 잡나:**
- 제네릭/캐스팅/`any` 가 쓰이면 빌드는 성공해도 런타임에 실패
- "존재하는가?" 와 "응답이 호출측 기대와 일치하는가?" 는 전혀 다른 검증

## 2. 통합 정합성 검증 — 교차 비교

QA 서브에이전트에 반드시 포함할 **교차 비교** 영역. 한쪽만 읽으면 못 잡는다.

### 2-1. 생산자 ↔ 소비자 shape 교차 검증
1. 생산자(API route 등)가 반환하는 객체의 shape 추출
2. 소비자(클라이언트 훅·호출부)가 기대하는 타입 확인
3. shape 일치 비교 — 특히 래핑(`{ data: [...] }`)을 소비자가 unwrap 하는지
4. 주의: 페이지네이션 래핑, snake_case↔camelCase, 즉시 응답 vs 최종 결과 차이

### 2-2. 파일 경로 ↔ 링크/라우터 경로 매핑
1. 페이지 파일 경로에서 URL 패턴 추출 (그룹·동적 세그먼트 고려)
2. 코드 내 모든 링크·라우팅 값 수집
3. 각 링크가 실제 존재하는 경로를 가리키는지 확인

### 2-3. 상태 전이 완전성 추적
1. 상태 전이 맵에서 허용 전이 목록 추출
2. 코드의 모든 상태 업데이트 추출
3. 각 업데이트가 맵에 정의됐는지(무단 전이 없음) + 맵의 전이가 코드에서 실행되는지(죽은 전이 없음)
4. 특히 중간 상태 → 최종 상태 전환 누락 여부

### 2-4. 엔드포인트 ↔ 호출부 1:1 매핑
1. 정의된 엔드포인트 목록 추출
2. 실제 호출하는 곳 목록 추출
3. 호출되지 않는 엔드포인트가 의도적(관리용)인지 누락인지 판단

> 위 패턴은 웹 앱에서 추출했지만 원리는 일반적이다: **계약을 가진 두 면(생산자·소비자)이
> 있으면, 양쪽을 동시에 열어 shape·이름·경로·상태를 대조한다.** CLI·라이브러리·데이터
> 파이프라인 등 도메인에 맞게 "두 면"을 식별해 적용하라.

## 3. QA 에이전트 설계 원칙

### 3-1. 검증과 실행이 가능한 도구를 부여하라
QA 가 읽기 전용이면 패턴 검색·자동 대조·테스트 실행을 못 한다. 효과적 QA 는:
- `Grep` 으로 패턴 검색 (모든 응답 반환부 추출)
- `Bash` 로 테스트·빌드·대조 스크립트 실행

**권장 tools**: `Read`, `Grep`, `Bash`. 정의에 "검증 → 리포트 → 수정 요청" 프로토콜을
명시한다 (QA 가 직접 고치기보다 비서·구현 에이전트에게 구체적 수정 요청을 내는 게 기본).

### 3-2. "존재 확인"보다 "교차 비교"를 우선하라

| 약한 체크 | 강한 체크 |
|----------|----------|
| 엔드포인트가 존재하는가? | 응답 shape 과 호출측 타입이 일치하는가? |
| 전이 맵이 정의됐는가? | 모든 상태 업데이트가 맵의 전이와 일치하는가? |
| 페이지가 존재하는가? | 모든 링크가 실제 페이지를 가리키는가? |
| strict mode 인가? | 캐스팅으로 우회된 타입 안전성이 없는가? |

### 3-3. "양쪽을 동시에 읽어라"
경계면 버그를 잡으려면 한쪽만 읽어선 안 된다. 생산자 **와** 소비자를, 전이 맵 **와**
업데이트 코드를, 파일 구조 **와** 링크를 **같이** 읽는다. 에이전트 정의에 이 원칙을
명시적으로 기재한다.

### 3-4. 빌드 후 1회가 아니라, 각 모듈 완성 직후에 (incremental QA)
QA 를 "전체 완성 후" 에만 배치하면 버그가 누적되고 초기 경계면 불일치가 후속 모듈로
전파된다. 오케스트레이션 스킬에서 **각 모듈 완성 시 즉시 해당 모듈 + 인접 경계면의
교차 검증**을 위임하도록 배치한다.

## 4. QA 에이전트 정의 템플릿

```markdown
---
name: qa-inspector
description: "QA 검증 전문가. 스펙 준수와 모듈 간 통합 정합성(경계면 교차 비교)을 검증. 모듈 완성·통합·검증·정합성 점검 요청 시 위임."
model: high
tools:
  - Read
  - Grep
  - Bash
---

# QA Inspector

## 핵심 역할
스펙 대비 구현 품질과 **모듈 간 통합 정합성**을 검증한다.

## 검증 우선순위
1. 통합 정합성 (가장 높음) — 경계면 불일치가 런타임 에러의 주요 원인
2. 기능 스펙 준수
3. 코드 품질 (미사용 코드, 명명)

## 검증 방법: "양쪽 동시 읽기"
경계면은 반드시 양쪽 코드를 동시에 열어 비교한다:

| 검증 대상 | 생산자 | 소비자 |
|----------|--------|--------|
| 응답 shape | 반환부 | 호출측 타입 |
| 라우팅 | 페이지 파일 경로 | 링크·라우팅 값 |
| 상태 전이 | 전이 맵 | 상태 업데이트 코드 |

## 입력/출력 프로토콜
- 입력: 검증 대상 파일 경로 (오케스트레이션 스킬이 프롬프트에 명시)
- 출력: `_workspace/{phase}_qa_report.md` — 통과/실패/미검증을 구분, 실패는 파일:라인 + 수정 방법

## 협업
- 발견 즉시 비서에게 구체적 수정 요청 (파일:라인 + 수정 방법)
- 경계면 이슈는 생산자·소비자 양쪽 모두 명시
```
