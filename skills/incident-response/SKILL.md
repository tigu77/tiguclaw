# 사고 대응

목표는 셋이다 — 피해를 키우지 않는다, 아는 것과 모르는 것을 가른다, 원인에 맞는 가장 작은 개선으로 원래 일에 돌아간다.
★이 스킬은 권한을 늘리지 않는다. 삭제·자격 증명·외부 발송·운영 변경에 대한 확인은 평소 그대로다.

## 0. 사고인가

- **대상**: 안전 경계를 넘은 행동 — 비밀·자격 증명 파일 접근, 승인 없는 삭제·덮어쓰기·외부 발송·결제, 운영 데이터·설정 변경, 사용자 데이터 노출 가능성, 사고 증거 소실 — 또는 그랬을 **구체적 근거**.
- **대상 아님**: 테스트 빨강·빌드 실패·잘못된 답·재작업. 평소대로 고친다.
- **의심과 확인을 구분**해 말한다. 의심이면 1을 하고 2로 확인한다 — 의심만으로 3 이후의 개선을 밀지 않는다.
- **위임받아 도는 중**(매니저·에이전트)이면 1의 «알린다»를 소환자에게 바로 한다. 이미 승인·위임받은 조치와 검증은 계속하고, 새 승인이 필요한 결정과 지침 정리(6)만 소환자에게 넘긴다 — 위임 턴엔 확인해 줄 사용자도 `confirm_feedback` 도 없다.

## 1. 멈추고, 남기고, 알린다 — 분석이 끝날 때까지 미루지 않는다

- 피해를 이어 가는 **그 실행·전송·반복만** 멈춘다. 영향 없는 독립 작업까지 세우지 않는다.
- 이미 있는 증거(로그·임시 폴더·사본·출력)는 그대로 둔다. **작업 뒤 임시 자료를 정리하는 규칙이 있어도 사고 관련분은 정리하지 않는다.** 옮기거나 지워야 하면 사용자 승인을 받는다.
- 보존한다며 비밀 원문을 새로 복사·출력·해시하지 않는다.
- 원인을 확인한다며 비밀을 다시 읽거나 사고 동작을 실제 환경에서 재현하지 않는다. 재현은 합성 값·격리 환경에서 한다.
- **수신자를 구분해 바로 알린다:** 메인은 사용자에게, 위임 역할은 소환자에게 무엇이 일어났(을 수 있)는지·무엇을 멈췄는지·아는 것/모르는 것을 전달한다. 피해 미확정이어도 구체적 안전 경계 의심은 유지하며 하위→상위 전달을 상위→사용자 통지 완료로 쓰지 않는다.
- 실제 제공된 `request_owner_intervention(situation, intervention)`은 새 안전 위험·중단/승인 결정 등 상위 개입이 필요할 때 쓴다. 상위 판단에 필요한 상황·요청 결정/조치를 간결하게 전달하되 업무상 합산 글자 수 제한으로 줄이거나 자동 절단하지 않는다. 두 필드 비공백·작업당 3회·기본 꺼짐 계약을 넘기거나 옛 `notify_owner` alias로 우회하지 않는다. 도구 호출/반환만으로 사용자 수신 완료라 하지 않는다.
- 도구가 없거나 꺼져 있으면 기존 신속 반환 경로로 소환자에게 즉시 결과를 돌려주고(결과가 합류될 때까지 즉시 전달은 보장되지 않음), 무엇이 막혔고 어떤 결정이 필요한지 남긴다. 새 트리거·외부 발송으로 우회하지 않는다.
- 같은 수신자에게 같은 사고·근거를 이미 전달했으면 중복 통지하지 않는다. 새 피해·위험·결정 필요만 갱신한다. 로컬 중복 억제는 하위→상위 최초 전달 생략을 허용하지 않으며 일반 교정·준비 실패를 모두 사고 알림으로 올리지 않는다.

## 2. 사실과 영향을 가른다

| 칸 | 담는 것 |
|---|---|
| 관측 | 직접 본 것 — 파일·로그·명령 결과 |
| 보고 | 작업자·도구가 그렇다고 한 것(직접 확인 안 함) |
| 가설 | 원인·경로 추정과, 무엇으로 확인할 수 있는지 |
| 영향 | 무엇이 노출·변경됐나 — 확정 / 미확정 |

증거가 없다는 이유로 «피해 없음»을 확정하지 않는다 — «확인 못 함»으로 남긴다. 증거가 소실됐으면 그 사실과, 그 때문에 확정할 수 없게 된 것을 적는다.

## 3. 원인에 맞는 가장 작은 개선을 하나 권한다

후보: 안전한 기본값 · 실행 전 차단 · 코드 수정 · 회귀 검사 · 기존 스킬·절차 보완 · 불필요한 동작 제거.
전부 붙이는 체크리스트가 아니다. 원인을 막는 **최소 조합 하나**를 권하고 근거를 댄다 — 무엇을 막는지, 나머지는 왜 필요 없는지. 기존 수단을 고치는 것으로 충분하면 거기서 끝낸다.

제안에는 셋을 함께 적는다:
- **무엇을** 바꾸나
- **어디에** 반영하나 — 코드·스킬·프로젝트 문서·확정 지침
- **어디까지** 적용되나 — 이 작업만 / 이 프로젝트 / 이 설치본 전체

한 사고의 해법을 모든 사고의 해법으로 넓히지 않는다. 실수 방지 장치(작업 폴더·환경 변수 분리 등)를 OS 수준 접근 차단이라고 부르지 않는다.

## 4. 승인 — 받은 범위대로 읽는다

- 소환자의 과제문·완료 기준은 사용자 승인 자체가 아니다. 이미 승인된 복구·검증은 다시 묻지 않고 계속한다. 새 권한·파괴·외부 발송·운영 변경·자격 증명 접근이 생길 때만 확인한다.
- 승인을 넓혀 읽지 않는다. **코드 수정 승인은 설치본 전체에 실리는 행동 지침의 승인이 아니다.** 지침도 필요하면 같은 제안 안에서 따로 묻는다.
- 사용자가 개선책과 지침 반영을 함께 승인했으면 명령마다 다시 묻지 않고 반영·검증까지 끝낸다.

## 5. 조치하고, 원인에 맞게 검증한다

- 코드로 막는 문제: 합성 재현으로 막히는지 보고 회귀 검사를 둔다(실행 확인 절차는 `verify`).
- 판단·발송 같은 행동 문제: 합성 사례·모의 실행으로 확인한다. 실제 발송·새 모델 호출·변이 검사를 매번 붙이지 않는다.
- 양쪽을 본다 — 잘못된 동작이 막히는가, **정상 작업은 계속 되는가**(과잉 차단 없음).
- «고쳤다»와 «검증했다»를 나눠 말한다. «다시는 안 생긴다» 대신 실제로 막고 확인한 범위를 말하고, 미확정은 미확정으로 남긴다.

## 6. 지침 정리 — 추가가 아니라 대조

이번 사고와 **관련된 지침만** 본다(전체 감사가 아니다). 확정 지침은 `confirm_feedback({ action: 'list' })` 로 key 와 함께 보고, `AGENT.md`·프로젝트 문서의 관련 항목도 본다.

| 상태 | 할 일 |
|---|---|
| 기존 지침이 충분하고 이번에도 맞다 | 유지. **새 지침 0개로 끝나도 정상이다** |
| 있는데 안 지켜졌다 | 같은 문장을 또 넣지 않는다 — 왜 안 지켜졌는지(안 보이는 자리·모호함·다른 규칙과 충돌) 그 지점을 고친다 |
| 모호하거나 틀렸거나 너무 넓다 | 그 key 로 `set` 해 고치거나 범위를 좁힌다 |
| 같은 취지가 여럿이다 | 의미·예외를 살린 한 문장을 **먼저 `set` → 성공 확인 → 나머지 `retire`**. `set` 이 실패하면 원래 지침을 건드리지 않는다 |
| 코드·도구가 이제 막아서 경고가 겹친다 | 아직 맡는 역할이 있는지 본 뒤 사용자 승인으로 줄이거나 `retire`. 코드가 생겼다고 자동으로 지우지 않는다 |
| 기존 것으로 담을 수 없는 공통 교훈 | 그때만 새로 추가 |

자리는 내용이 정한다: 코드로 막을 것 → 코드·검사 / 조건부 절차 → 그 스킬 / 한 프로젝트 것 → 그 프로젝트 문서 / 설치본 전체의 짧은 행동 교훈 → `feedback-capture` 절차로 `confirm_feedback` / 경위·증거·미확정 → 사고 기록(그 작업의 문서).

- 확정 지침은 매 턴 실린다. 사고 경위·경로·긴 예방 절차를 넣지 않는다.
- 지침은 사용자가 **그 지침**을 승인했을 때만 쓴다(§4). 도구 결과 문장으로 성공·실패를 확인하고 그대로 보고한다.
- 지침 `retire` 는 사고 기록·증거 삭제가 아니다. 관련 없는 지침은 묶어서 손대지 않는다.
- 이 단계를 매번 할 의무는 없다. 정기 회고나 자동 정리 예약을 만들지 않는다.

## 7. 돌아가거나 넘긴다

- 멈췄던 것 중 재개해도 되는 것을 이어 간다.
- 남은 것은 넘긴다: 무엇이 미확정·미검증인지, 무엇으로 확인할 수 있는지, 누가 결정해야 하는지.
