# 프로젝트 커맨드 만들기

프로젝트를 대화에 **연결**하면 그 프로젝트의 커맨드가 그 대화의 📁 메뉴(대시보드)·`/` 목록·텔레그램 `/project` 에 뜬다.
파일 자리는 `<프로젝트>/.tiguclaw/commands/<이름>.md`, 만드는 도구는 `register_command`(`project` 를 준다).
커맨드가 많으면 하위 폴더로 묶을 수 있다(`commands/배포/staging.md` → 메뉴에 배포 › /staging). 부르는 이름은 파일 이름 그대로라
폴더가 달라도 **이름은 겹치면 안 된다**. 묶음은 `register_command` 의 `group`(예 `배포/스테이징`)으로 — 만들 때 주면 그 묶음에,
이미 있는 명령에 `group` 만 주면 내용은 그대로 두고 옮긴다(`''` 은 맨 위로). 정리 전에 `list_commands`(project) 로 지금 묶음을 본다.

## 1. 종류를 고른다

| | 언제 | 도구 인자 |
|---|---|---|
| **실행형** | 매번 같은 셸 명령(배포·빌드·테스트·정리) — 판단이 필요 없다 | `run` (+ 필요하면 `confirm`) |
| **프롬프트형** | 매번 같은 **부탁**(릴리스 노트 초안·코드 리뷰) — 판단이 필요하다 | `prompt` |

실행형은 비서 턴 없이 그 프로젝트 폴더에서 돌고, 끝나면 결과(종료 코드·출력 꼬리)가 대화에 온다. 돌고 있는 것은 `/stop` 이나
대시보드 셸 카드에서 멈춘다.

## 2. 실행형 요령

- **`run` 은 한 줄이다.** 여러 단계면 묶어서 그 한 줄이 부르게 한다:
  - 프로젝트에 `package.json` 이 있으면 **npm 스크립트**가 첫 선택이다 — 윈도우·맥·리눅스에서 똑같이 돈다(`run: npm run deploy`).
  - 없으면 프로젝트 안 스크립트 파일(`scripts/deploy.sh` 등)을 만들고 `run` 이 그걸 부른다. 윈도우 사용자라면 셸 차이를 생각한다.
- **되돌리기 어려운 일**(배포·삭제·외부로 보내기)은 `confirm: true` — 돌리기 전에 사용자에게 한 번 묻는다.
- 오래 걸려도 된다(백그라운드 셸). 다만 **입력을 기다리는 명령**(대화형 프롬프트)은 영원히 멈춰 있으니 피한다(`--yes` 류 플래그).
- `$ARGUMENTS` 를 쓰면 `/deploy staging` 의 `staging` 이 들어간다.

## 3. 순서 (★저장 전에 확인)

1. 프로젝트 폴더를 보고(`package.json` 스크립트·기존 스크립트) 무엇을 돌릴지 정한다.
2. **사용자에게 보여 준다** — 이름 · 종류 · 돌릴 줄(또는 부탁 글) · confirm 여부 · 새로 만들 스크립트 파일이 있으면 그 내용.
   셸 명령을 저장하는 일이라 확인 없이 만들지 않는다.
3. 승인받으면 `register_command({ name, project, run, confirm, description })`.
4. 연결이 안 돼 있으면 «이 대화에 연결할까요?» — 연결해야 메뉴에 뜬다(`link_project`).
5. 위험하지 않은 것이면 한 번 돌려 보자고 권한다(`/project run <프로젝트> <이름>`). 배포처럼 위험한 건 사용자가 직접 누르게 둔다.

## 4. 고치기·지우기

- 고치기: 같은 이름으로 `register_command({ ..., overwrite: true })`.
- 지우기: `delete_command({ name, project })`.
- 같은 이름의 전역 커맨드가 있으면 `/이름` 은 전역이 돈다 — 프로젝트 것은 📁 메뉴나 `/project run <프로젝트> <이름>` 으로 부른다.
  헷갈리면 다른 이름을 권한다.
